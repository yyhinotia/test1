# Pawns 信息卡分阶段需求设计文档

**版本：V0.1**  
**状态：草案**  
**适用项目：《修仙宗门 / 修士人生模拟》**  
**核心定位：Pawn 信息卡不是传统 RPG 属性面板，而是“修士身份 + 当前状态 + Build + 成长路径”的统一 UI 入口。**

---

## 一、设计目标

信息卡必须优先回答五个问题：

```text
我是谁？
我现在是什么境界？
我是什么流派？
我带了什么 Build？
我下一步怎么成长？
```

设计原则：

1. **身份优先，Build 优先于数值。**
2. **真实 Pawn 数据绑定，不做假数据角色卡。**
3. **事件驱动刷新，不每帧刷新 UI。**
4. **突破 = Build 容量扩展，而不是单纯数值提升。**
5. **MVP 做减法，关系、宗门贡献、好感度不进入第一版。**
6. **UI 不塞进 Pawn 对象，采用 Pawn → PawnData → PawnInfoPanel。**

---

## 二、总体信息架构

最终形态：

```text
身份
 ↓
当前战斗状态
 ↓
Build
 ↓
成长 / 突破
 ↓
详细属性 / 扩展信息
```

信息优先级：

```text
身份 > 资源状态 > Build > 成长 > 详细属性
```

长期布局目标：

```text
左侧：人物 / 状态
中间：气血、真元、护体、核心属性
右侧：Build
底部：境界成长 / 突破
```

---

## 三、统一数据契约

所有阶段共享同一套数据边界：

```text
PawnData
├── Identity
│   ├── name
│   ├── realm
│   ├── sub_realm
│   ├── spirit_root
│   ├── path
│   └── build_tag
│
├── Vital
│   ├── hp / max_hp
│   ├── qi / max_qi
│   ├── shield / max_shield
│   └── spirit / max_spirit
│
├── Attributes
│   ├── attack
│   ├── spell_power
│   ├── defense
│   ├── attack_speed
│   ├── movement_speed
│   └── crit_rate
│
├── Cultivation
│   ├── current_exp
│   ├── required_exp
│   ├── next_realm
│   └── breakthrough_conditions[]
│
└── Build
    ├── cultivation_method
    ├── weapon
    ├── active_skills[]
    ├── passive_skills[]
    └── capacity
        ├── method_current / method_max
        ├── active_current / active_max
        └── passive_current / passive_max
```

UI 只读 PawnData，不直接修改 Pawn 节点。更换技能、突破等操作通过命令或请求层执行。

# 四、分阶段需求

## Phase 0：数据契约与 UI 骨架

### 目标

先跑通：

```text
Pawn → PawnData → PawnInfoPanel
```

不做完整界面，只建立正确绑定关系。

### 需求

- 定义 `PawnData` 数据结构。
- 定义 `PawnInfoPanel` 骨架。
- 支持 `bind_pawn(pawn_data)` 与 `unbind()`。
- 定义关键信号：
  - `vital_changed`
  - `attributes_changed`
  - `build_changed`
  - `cultivation_changed`
  - `realm_changed`
- 点击战场 Pawn，能绑定并显示姓名。

### 验收标准

- 点击不同 Pawn，信息卡显示真实数据。
- HP 变化时 UI 自动刷新。
- UI 节点不持有 `hp_label` 这类字段到 Pawn 对象中。
- 解绑后不再接收旧 Pawn 信号。

### 不做

- 立绘
- 详细属性
- 人物关系
- 复杂动画

---

## Phase 1：MVP 最小信息卡

### 目标

让玩家在战斗和暂停中快速看懂：

```text
这个修士是谁、什么境界、什么 Build、当前状态如何。
```

### 推荐形态

紧凑侧栏或中等窗口，不追求 16:9 完整面板。

```text
┌──────────────────────────────┐
│ 林玄                         │
│ 炼气 · 三层                  │
│ 火灵根 · 火修                │
│ 🔥 赤炎飞剑流                │
├──────────────────────────────┤
│ 气血  ████████ 120/120       │
│ 真元  ██████░░ 85/100        │
│ 护体  ███░░░░░ 40/40         │
├──────────────────────────────┤
│ 攻击 32   法强 41   防御 18  │
│ 攻速 1.2  移速 4.5  暴击 5%  │
│ [详细属性]                   │
├──────────────────────────────┤
│ BUILD                        │
│ 功法：赤炎诀 1/1             │
│ 武器：赤炎剑                 │
│ 主动：火球 / 飞剑 2/2        │
│ 被动：火灵体 1/1             │
├──────────────────────────────┤
│ 修为 ███████░░░ 72% → 筑基   │
│ [查看突破]                   │
└──────────────────────────────┘
```

### 需求

- 显示身份四行：姓名、境界、灵根/路线、Build 标签。
- 显示三层资源：气血、真元、护体。
- 显示核心属性：攻击、法强、防御、攻速、移速、暴击。
- 显示 Build 摘要：功法、武器、主动、被动数量。
- 显示修为进度与下一境界。
- 点击战场 Pawn 打开。
- 战斗中可精简显示，暂停时可完整显示。

### 验收标准

- 玩家打开后 3 秒内能说出“这个修士是什么流派”。
- Build 摘要比详细属性更醒目。
- HP、真元、护体变化实时刷新。
- 不显示关系、好感度、宗门贡献、社会地位。

### 不做

- 人物立绘
- 状态图标系统
- 装备详情页
- 功法研究树
- 人物关系

---

## Phase 2：Build 信息卡

### 目标

把 Build 做成信息卡最突出的区域，并可视化 Build 容量。

### 推荐布局

右侧 Build 区：

```text
BUILD
────────────────────
修炼功法  1 / 1
┌──────────────────┐
│ 🔥 赤炎诀        │
│ 火系 · 主修       │
└──────────────────┘

武器
┌──────────────────┐
│ ⚔ 赤炎剑         │
│ 法器 · 火         │
└──────────────────┘

主动技能  2 / 2
[🔥 火球] [⚔ 飞剑]

被动技能  1 / 1
[🔥 火灵体]
```

### 需求

- 功法槽、武器槽、主动技能槽、被动技能槽。
- 每个槽位显示当前 / 最大容量。
- 点击槽位查看详情。
- 支持从详情入口更换功法、武器、技能。
- 更换后 Build 标签同步刷新。
- 突破后容量增加时，槽位 UI 立即更新。
- 最低限度显示冲突、属性要求、五行要求。

### 验收标准

- 玩家能一眼看出“突破后我多了哪些 Build 空间”。
- 更换主动技能后，右侧 Build 区无需重开面板即可刷新。
- 功法不只是显示 `+10% 攻击`，而要显示战斗方式标签。
- Build 容量与境界数据一致。

### 不做

- 完整功法树
- 深度研究系统
- 复杂词条对比
- Build 分享

---

## Phase 3：成长与突破信息卡

### 目标

让突破成为 Build 重构节点，而不是普通升级。

### 推荐布局

底部成长区：

```text
炼气 · 三层
██████████████░░░░ 72%

下一境界：筑基

突破条件：
✓ 修为达到要求
✓ 筑基丹
✗ 灵石 500

突破后预览：
功法槽 +1
主动技能槽 +1
被动技能槽 +1
解锁：筑基级功法 / 装备

[查看突破]
```

### 需求

- 显示当前境界、小境界、修为进度。
- 显示下一境界。
- 显示突破条件完成状态。
- 显示突破后 Build 容量预览。
- 提供“查看突破”入口，进入独立突破页面。
- 不直接在主信息卡上做“点击突破”。

### 验收标准

- 突破条件状态与数据一致。
- 突破后容量预览正确。
- 突破完成后，信息卡境界、修为、Build 容量全部刷新。
- 玩家理解“突破 = 新玩法空间”。

### 不做

- 复杂材料链
- 一键突破
- 突破动画大片
- 渡劫小游戏

---

## Phase 4：完整修士档案

### 目标

成为未来所有角色系统的统一入口。

### 可加入内容

- 状态图标：灼烧、重伤、中毒、灵力紊乱。
- 详细属性折叠页。
- 装备详情。
- 功法详情与研究。
- 人物关系：师徒、同门、道侣。
- 宗门身份：外门、内门、真传、长老。
- 宗门贡献。
- Build 保存 / 分享。
- NPC / 敌人 Build 查看。
- 战斗 AI 使用 Build 标签。
- 推荐装备、功法联动。

### 注意

这些内容属于第二阶段或更后期。  
第一版 MVP 不应出现：

```text
关系
好感度
道侣
家族
宗门贡献
社会地位
```

否则 UI 会反向推动系统膨胀。

---

# 五、跨阶段交互规则

1. **点击战场 Pawn → 打开 PawnInfoPanel。**
2. **战斗中：精简信息卡或侧栏。**
3. **暂停时：可打开完整信息卡。**
4. **非战斗：完整信息卡。**
5. **数据变化：信号驱动刷新。**
6. **更换 Build：通过命令层执行，不直接改 UI。**
7. **只允许一个主信息卡实例，避免多面板混乱。**

# 六、Godot 技术实现建议

推荐节点：

```text
PawnInfoPanel
├── HeaderSection
├── VitalSection
├── AttributeSection
├── BuildSection
├── CultivationSection
└── DetailTabs
```

推荐数据流：

```text
Pawn 节点
 ↓
PawnData Resource
 ↓
PawnInfoPanel.bind_pawn(pawn_data)
 ↓
信号刷新 UI
```

禁止：

```gdscript
pawn.hp_label
pawn.weapon_icon
pawn.build_panel
```

推荐：

```gdscript
pawn_data.vital_changed.connect(_on_vital_changed)
pawn_data.build_changed.connect(_on_build_changed)
```

# 七、总验收清单

| 阶段 | 必须验证 |
|---|---|
| Phase 0 | 真实数据绑定、信号刷新、UI 不侵入 Pawn |
| Phase 1 | 身份、资源、核心属性、Build 摘要、修为进度 |
| Phase 2 | Build 槽位、容量、更换刷新、冲突提示 |
| Phase 3 | 突破条件、容量预览、突破后刷新 |
| Phase 4 | 状态、详细属性、关系、宗门、Build 分享 |

---

# 八、风险与控制

| 风险 | 控制 |
|---|---|
| 变成属性垃圾场 | Build 优先，详细属性折叠 |
| UI 反向推动系统膨胀 | MVP 不显示关系、宗门贡献、好感度 |
| 假数据角色卡 | 第一版就绑定真实 PawnData |
| 每帧刷新性能差 | 事件驱动，信号刷新 |
| 战斗中被面板打断 | 战斗中精简，暂停时完整 |
| 突破只是数值提升 | 突破必须显示 Build 容量扩展 |

---

# 九、最终路线结论

推荐按以下顺序推进：

```text
Phase 0：数据契约与 UI 骨架
Phase 1：MVP 最小信息卡
Phase 2：Build 信息卡
Phase 3：成长与突破信息卡
Phase 4：完整修士档案
```

一句话总结：

> **先让信息卡成为真实 Pawn 数据的 Build 与成长入口，再逐步扩展为完整修士档案。MVP 阶段必须做减法，核心只保留“我是谁、我什么境界、我什么 Build、我下一步怎么成长”。**
